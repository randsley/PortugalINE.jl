Joining

PortugalINE.Join — Module

Joining indicators to geometry, which is where the two halves of this package meet and where the errors are silent.

join_municipal takes a MunicipalBoundaries and one or more IndicatorData extracts and returns a MunicipalDataset: one row per municipality present in all of them, in DICO order, with a contiguity matrix built over exactly those units and nothing else.

Why the key is the DICO, measured

Indicator 0014580 is published on NUTS 2024 and 0008074 on NUTS 2013. Both carry all 308 municipalities. Joining them:

keymatches
NUTS code (geocod)132 of 308
name (geodsg)305 of 308
DICO308 of 308

Lisboa is 1A01106 under NUTS 2024 and 1701106 under NUTS 2013, so a join on the code INE returns as its primary identifier loses 57% of the country without raising anything. A join on name is worse than its 305 suggests: the three mismatches are Calheta (R.A.M.) against Calheta and two like it, and Calheta is two different municipalities — 3101 in Madeira and 4501 in the Azores — so a name join is ambiguous rather than merely incomplete.

The DICO is the last four characters of either code, and it is stable because it is the official district-and-municipality number rather than a statistical grouping. municipal_values keys on it, this layer joins on it, and the GAL files from write_gal are ordered by it, so the data and the matrix line up without a lookup table.

Why the matrix is rebuilt and not sliced

Dropping a unit changes its neighbours' degrees, so a row-standardised W from the full set is wrong for any subset of it: the surviving rows no longer sum to one. Everything here therefore carries binary adjacency and standardises last — spatial_weights on the dataset, and model_matrix again after dropping incomplete cases. A unit left with no neighbours is named in the error rather than divided by zero.

The islands

The 30 island municipalities have data and no land neighbours. CAOP serves the mainland as its own collection, so the usual join silently settles on 278 units — which is the right answer and the wrong way to reach it. Every unit dropped is recorded on the dataset, and the ones dropped for being islands are counted separately from the ones dropped for anything else, because the second kind means a vintage or coverage problem and the first does not.

PortugalINE.Join.MunicipalDataset — Type
MunicipalDataset

One row per municipality (or parish), aligned with a contiguity structure over exactly those units. The level is the boundaries' own: ds.boundaries.level.

fieldwhat
dicothe join key, sorted; the row order of everything else. For parishes it holds the DICOFRE
namethe municipality name
columnsa NamedTuple of one Vector{Union{Float64, Missing}} per indicator
nutsa NamedTuple of the NUTS codes each indicator supplied, as a vintage record
boundariesthe geometry, subset and reordered to match dico
adjacencybinary contiguity in dico order; standardise with spatial_weights
criterion:queen or :rook, as built
varcds, periodsthe INE code and reference period per column, in column order
extractedthe earliest extraction timestamp among the sources
filters, languages, column_extractedper column: the dimension filter sent (Dict(3 => "T")), the language, and that extract's own extraction timestamp

columns and nuts are NamedTuples of equal-length vectors, so each is already a valid Tables.jl column table. adjacency is deliberately not row-standardised; see this module's documentation for why.

PortugalINE.Join.dropped — Method
dropped(ds) -> NamedTuple

What the join left out, as three vectors of DICO codes: geometry (a boundary with no data in some indicator), data (data with no boundary, excluding islands, with a value), islands (data with no boundary because the unit is in Madeira or the Azores, which CAOP serves as separate collections), and empty (listed in the data with no value and no boundary: units of another map, as the area indicator 0011866 lists the 302 parishes restored in 2025 beside the 2,882 of the 2013 map).

The split matters. Islands dropping out is expected and is not a fault. A mainland municipality dropping out means the extracts disagree about what exists, which is a vintage or coverage problem worth looking at before the estimates are believed.

PortugalINE.Join.join_municipal — Method
join_municipal(b::MunicipalBoundaries, specs...; criterion = :queen)

Join one or more indicator extracts to boundaries on DICO, and build a contiguity structure over the municipalities present in all of them.

Boundaries read with level = :parish are joined on DICOFRE instead, to the parish rows of each extract (see parish_values); the rest is the same.

Each spec is :column_name => data, or :column_name => (data, period) when the extract covers more than one period.

b  = read_caop_geojson("caop_municipios.json")
pp = indicator_data("0014580"; period = "2023")
de = indicator_data("0013189"; period = "2023")
ds = join_municipal(b, :purchasing_power => pp, :density => de)

W = spatial_weights(ds)                       # row-standardised
m = model_matrix(ds, :purchasing_power, :density)

The result is an inner join: a municipality missing from any one extract is dropped from all of them, so every column has the same length and the same meaning per row. What was dropped is kept — see dropped — and anything the join noticed but did not treat as fatal is in notes.

PortugalINE.Join.model_matrix — Method
model_matrix(ds, y::Symbol, xs::Symbol...; standardize = true, intercept = false)

Everything an estimator needs, over the rows where y and every x are all present: (y, X, W, dico, xnames, dropped).

W is rebuilt over the surviving rows, not sliced out of the dataset's matrix, because a row-standardised matrix is only valid for the units it was computed over. If dropping incomplete cases leaves a unit with no neighbours, that is an error naming the unit rather than a division by zero.

m = model_matrix(ds, :purchasing_power, :log_density, :ageing)
fit_spatial(SAR(), m.W, m.X, m.y)

PortugalINE.Join.notes — Method
notes(ds) -> Vector{String}

Everything the join noticed and did not treat as fatal, in the order it was noticed: units dropped and why, names the indicators disagreed on, NUTS vintages that differ between extracts, and units left without neighbours. Printed by show, and worth reading before the first regression.

PortugalINE.Join.spatial_weights — Method
spatial_weights(ds; standardize = true) -> SparseMatrixCSC

The contiguity matrix over the dataset's municipalities, row-standardised by default.

Standardising happens here rather than when the dataset was built, because dropping a unit changes its neighbours' degrees: a standardised matrix is only valid for the exact set of units it was computed over.

PortugalINE.Join.write_dataset — Method
write_dataset(dir, ds; name = "portugal_municipalities", gal = true,
              centroids_file = true) -> Vector{String}

Write the dataset out as the three files an analysis elsewhere actually needs, and return their paths:

filecontents
<name>.csvdico, name, one column per indicator
<name>_<criterion>.galthe contiguity structure, GeoDa GAL, in DICO order
<name>_centroids.csvarea-weighted centroids, for distance weightings
<name>_PROVENANCE.mdthe citations, the counts, and every note from the join

This is the handoff. GAL and CSV cross the gap as small text files that nothing at the far end has to parse a polygon or hit a network to read, and because both are ordered by DICO they line up by sorting alone. The provenance file is written because INE's reuse condition and CAOP's licence both require a credit, and a credit that lives only in a README travels badly.
