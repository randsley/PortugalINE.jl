Boundaries and weights

PortugalINE.Boundaries — Module

Municipal boundaries, and spatial weights built from them.

The boundaries come from CAOP, the Carta Administrativa Oficial de Portugal, which Direção-Geral do Território publishes through an OGC API and licenses CC-BY-4.0 with public access unrestricted. Reuse requires the credit DGT specifies; see CAOP_ATTRIBUTION.

Why there is no geometry dependency

Contiguity here is computed by hashing vertices and edges, not by intersecting polygons, because CAOP is a clean planar partition: where two municipalities share a border, both rings carry the same vertices, to the bit. That was measured rather than assumed. Hashing exact Float64 pairs and hashing coordinates rounded to six decimals give the identical graph over the 278 mainland municipalities: 739 queen links, mean degree 5.32, no isolated unit. If rounding had changed the answer the topology would have been dirty and a geometry engine would have been needed; it did not, so GEOS, ArchGDAL and their build chains are all avoidable, and reading a GeoJSON plus hashing tuples is exact.

This holds for CAOP. It is not a general property of shapefiles, and contiguity reports enough for a caller to check it on data of their own: a planar partition that is not node-matched shows up as isolated units or an implausibly thin graph.

Queen and rook

Queen contiguity joins municipalities sharing at least one vertex; rook requires a shared edge, meaning two consecutive vertices in common. On the mainland the two differ by exactly two pairs, both meeting at a single point: Mêda with Sernancelhe, and Lisboa with Vila Franca de Xira. The distinction is usually taught in the abstract; on these data it is two named pairs out of 739, which is worth knowing before treating the choice as consequential.

PortugalINE.Boundaries.MunicipalBoundaries — Type
MunicipalBoundaries

Polygon rings for a set of municipalities or parishes, with their codes and names. Despite the name it holds either level; level says which.

Fields

  • codes: the DICO of each municipality, or the DICOFRE of each parish, in feature order.
  • names: the unit names.
  • rings: for each unit, its rings. A unit with islands or exclaves has more than one, and every ring is used for contiguity, so an exclave's neighbours are found as readily as the main body's.
  • level: :municipality or :parish.
  • source: the file the boundaries were read from (its name, not its path).
  • sha256: the SHA-256 of that file's bytes, which pins the exact vintage.
  • edition: the CAOP edition as the caller states it ("CAOP2024"), or "". It cannot be read from the file, and it matters: INE's parish figures join to CAOP2024 and not to CAOP2025 (see read_caop_geojson).

b[idx] subsets and reorders the units and keeps the provenance.

PortugalINE.Boundaries.centroids — Method
centroids(b) -> Matrix{Float64}

An n x 2 matrix of polygon centroids, one row per municipality, in the coordinates the boundaries carry.

The centroid is the area-weighted centroid of the rings, computed by the standard polygon moment formula, not the mean of the vertices: vertices cluster where a border is intricate, so averaging them pulls the result toward the fiddly side of the municipality. For a municipality of several rings the rings are combined by signed area, which also makes holes subtract as they should.

A degenerate ring of zero area falls back to its vertex mean, since the moment formula divides by that area.

PortugalINE.Boundaries.contiguity — Method
contiguity(b; criterion = :queen, standardize = false) -> SparseMatrixCSC{Float64,Int}

A contiguity weights matrix over the municipalities of b, in feature order.

With standardize = true the rows are divided by their sums. That throws if any row is empty rather than producing NaN: an isolated unit means either that the boundaries are not a node-matched planar partition, or that island municipalities have been mixed in with the mainland, and both are worth hearing about before the matrix reaches an estimator.

The matrix is symmetric and has a zero diagonal. On mainland CAOP it holds 739 non-zero pairs under :queen and 737 under :rook.

PortugalINE.Boundaries.knn_contiguity — Method
knn_contiguity(b, k; standardize = false) -> SparseMatrixCSC{Float64,Int}

A k-nearest-neighbour weights matrix from the centroids, by Euclidean distance.

Unlike contiguity this gives every unit exactly k neighbours, so it is the answer when island municipalities must be kept: no row is empty and the matrix row-standardises. The price is that it is not symmetric — being among your k nearest does not make you one of theirs — and estimators that assume a symmetric W will be wrong on it. Symmetrise deliberately if you need that, and say which way.

On lon/lat coordinates the distance is planar in degrees, which distorts with latitude. Over mainland Portugal, about 4 degrees of latitude, the distortion is small; project the coordinates first if it matters.

PortugalINE.Boundaries.read_caop_geojson — Method
read_caop_geojson(path; level = :municipality, code_property, name_property)

Read municipal or parish boundaries from a CAOP GeoJSON feature collection, as DGT's OGC API serves it:

https://ogcapi.dgterritorio.gov.pt/collections/municipios/items?f=json&limit=400

That collection is the mainland: 278 municipalities, which is the set with a connected contiguity graph. The 30 island municipalities of Madeira and the Azores are published separately and have no land neighbours at all, so a contiguity matrix spanning all 308 has 30 zero rows and cannot be row-standardised.

code_property must name a property holding the DICO; in CAOP it is dtmn. Each is checked to be four digits, because the DICO is what joins these boundaries to INE's indicators and a silent mismatch there is unrecoverable later.

With level = :parish the defaults are code_property = "dtmnfr" and name_property = "freguesia", and each code is checked to be a DICOFRE (four digits, then two digits or capital letters; see dicofre). DGT's API serves only the current CAOP, whose parish map is not the one INE publishes on (see parish_values); an older vintage comes as a GeoPackage, which scripts/caop_gpkg_to_geojson.py converts to this format with the coordinates unchanged.

The file is large — the full mainland collection is about 200 MB of JSON for 1.25 million vertices — so expect this to take a few seconds and a few gigabytes of transient memory.

The result records where it came from: the file name, the SHA-256 of its bytes, and edition if given (edition = "CAOP2024"). The file does not say which CAOP edition it is, so state it; write_dataset writes all three into the provenance file.

PortugalINE.Boundaries.write_gal — Method
write_gal(path, b; criterion = :queen, id = :code)

Write the contiguity graph as a GeoDa GAL file, the format SpatialEconometrics.jl already reads for the Columbus data. This is how the boundaries reach that package without it gaining any dependency on this one: the GAL file is committed, and nothing at the far end has to parse a polygon or reach the network.

id is :code to label units by DICO, or :name by municipality name. DICO is the better choice — it is what joins to INE's indicators. :name is refused when any name contains whitespace or repeats, because GAL splits fields on whitespace and a repeated id merges two units: on real CAOP it is refused (Vila Franca de Xira; two municipalities are called Calheta).

The first line is 0 n <name> <idvar>, as GeoDa writes it, then for each unit a line giving its id and neighbour count followed by a line of neighbour ids.
